# Browser viewing

When someone watches a camera in a browser through NeuroWatch Cloud, the recorder sends the camera's own compressed video. It decodes nothing for that, with one exception: an H.265 camera, for a browser that cannot play H.265, when the camera has no H.264 stream. This page covers the recorder's side only.

<a id="pass-through"></a>
## Pass-through, not transcoding

Browser live view subscribes to the camera's shared connection like any other reader. Each video unit is rewritten to Annex-B, with the stream's parameter sets put in front of every keyframe. That is byte rewriting; nothing is decoded. The units are handed to WebRTC through a pass-through track, which sends them as they are. H.264 and H.265 both work this way.

The recorder uploads each camera stream once to a media server, which forwards it to every viewer, and only while someone watches. Each delivery is authorised by a short-lived grant that the recorder checks itself.

The WebRTC library the recorder uses is patched in three places so pass-through works: it always advertises the pass-through formats (a desktop has no H.265 encoder to offer), it uses one peer connection per direction, and it trusts the pass-through sender's rate control, so its frame dropper cannot discard the catch-up pictures at the start of a view and corrupt it.

> **Why.** Transcoding costs a decoder and an encoder per stream and loses quality. Passing the camera's video through costs a copy of bytes, and what the viewer sees is what the camera recorded.

<a id="fast-start"></a>
## Starting without waiting for a keyframe

- A new publication holds back what a viewer could start from (keyframes, and what queued while it joined the media server) until the first viewer's keyframe request, so that viewer starts from the cached GOP exactly once. Meanwhile it sends the camera's newest pictures, which nothing can start from: the media server asks for a keyframe only when it has a viewer and a picture it cannot forward to it. Without a request the GOP goes out half a second after the viewer subscribed (at once when the source has no new pictures, such as a recording opened paused), and after 2 seconds at the latest.
- That start is the camera's whole current GOP, however long ago its keyframe was. Live view's queue limits (see [Per-subscriber queues](stream-engine.md#queues)) count what comes after it, and the queue to the media server holds a whole GOP while the recorder is still joining.
- A viewer's keyframe request is answered by sending the current GOP again from the cache, not by asking the camera, which many cameras ignore.
- Units handed to WebRTC are spaced 3 ms apart, because its sending stage keeps only the newest of pictures that arrive together; a burst would lose its keyframe.

> **Why.** Without these, a viewer joining mid-GOP waits for the camera's next keyframe, which can be several seconds away, or sees a corrupted start. Sending the GOP as soon as the media server reported a subscriber lost it: the browser was not taking video yet, and a new track's first pictures are dropped while its sender starts. Keeping only the first 2 seconds of a GOP made a viewer who started later than that wait for the next keyframe after all.

> **Why.** The media server has a part in this too. A browser hides its local network address, so the media server learns it only from the browser's first packet. A media server doing full ICE then waits up to a second before it accepts that route, and every view starts that much later; one in ICE lite mode accepts at once. The recorder itself is not affected.

<a id="catch-up"></a>
## Catch-up stamping

Catch-up pictures (a GOP sent again, or the pictures a replay decodes through before a sought moment) are stamped 1 ms apart, ending now. The viewer keeps them out of sight until pictures advance at real pace, so the start never visibly fast-forwards. After a seek in playback, the first replayed picture is stamped 1 ms after the previous one, so old video still on its way is never shown as the seek's.

<a id="playback-in-the-browser"></a>
## Playback in the browser

Browser playback replays the recording's own compressed units, read from the segment files and paced by their timestamps, into the same kind of pass-through track. Nothing is decoded or re-encoded.

<a id="sound"></a>
## Sound

Browsers cannot take AAC or G.711 over WebRTC, so the sound (and only the sound) is decoded to 48 kHz mono and published as an audio track, which the WebRTC stack encodes as Opus. A camera without sound gets no audio track.

<a id="transcoding"></a>
## When a browser can't play H.265

The viewer chooses in this order:

1. Play the stream as it is.
2. For an H.265 stream the browser cannot play, show the camera's H.264 stream instead, if it has one. That costs nothing.
3. Otherwise, ask the recorder to convert, if it reports that it can.

A conversion is shared by every such viewer of that stream: one decoder, then one H.264 encoder on the graphics card (VA-API, NVENC, Quick Sync, Media Foundation or V4L2). x264 (GPL) and OpenH264 (whose patent licence covers only Cisco's own binaries) are never used. If no hardware encoder works, each viewer gets VP8 encoded on the CPU from the shared decoder. The conversion stops when its last viewer leaves, and while it runs the viewer sees a note saying so and Diagnostics draws it.

> **Trade-off.** This is the one place the recorder decodes and encodes video for someone not at the desktop. It is the last resort, after the camera's own H.264 stream, and it is never hidden.

<a id="thumbnails"></a>
## Thumbnails and connection tests

A portal thumbnail comes from the recording's latest keyframe, decoded once; else from the camera's own ONVIF JPEG snapshot; else from one keyframe of its stream. A picture never opens a camera connection while one of the camera's streams is already open. Testing a camera from the portal reads its codec, size and frame rate from the stream parser, without decoding.

> **Not done or not measured.** The cloud's side (accounts, relaying, the media server) is not described in these pages. The recorder links to it outbound only; no port is opened on your network.
